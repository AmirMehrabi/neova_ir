# Neova board and project UX audit

Date: 2026-09-30. Scope: board interactions, task editor, collaboration updates, project discovery/settings/deletion, and shared navigation. This is a code-based expert review with focused executable checks and external primary-source research. No available browser session was exposed by the computer-use tool, so production WebSocket health, rendered contrast, device behavior, and observed usability have not been verified. No production data or application implementation was changed. Recommendations are proposals, not shipped fixes.

## Main recommendation

Repair state synchronization before changing the visual design. The originating browser must receive authoritative state from every successful mutation without depending on its own WebSocket event. Then make project management a labeled, direct action and improve feedback, recovery, and keyboard/mobile access.

## What explains the reload symptom

The app uses HTTP for writes, `toOthers()` for broadcasts, and a full-board HTTP snapshot when another socket reports a change. `resources/js/realtime.js` adds `X-Socket-ID` to fetch requests. Therefore the originating connection is deliberately excluded from its own event. This is a valid pattern only when the mutation response completely updates that client's state. Laravel documents this behavior in its [broadcasting guide](https://laravel.com/framework/docs/13.x/broadcasting#only-to-others).

Several write paths only update part of local state. Reloading retrieves fresh server state and can temporarily hide these defects. They are confirmed code defects; whether they explain every reported incident still requires live reproduction.

| Priority | Finding and evidence | Consequence | Recommended resolution |
| --- | --- | --- | --- |
| P0 | `BoardController::moveTask` returns only `success`; board `moveTask()` retains the task's old `updatedAt`. `TaskWorkflowService::move` updates timestamps and completion/block fields, including sibling positions. | Moving and then editing a task can produce a 409 conflict against the user's own move. Done/block indicators can also remain stale. Siblings affected by reordering may have stale versions too. | Return canonical affected task/column state and reconcile it in the originating client. Cover siblings, not just the dragged card. |
| P0 | `applyBulkAction()` changes selected local fields but does not reconcile new versions. `stateTask()` applies only a subset of task fields; `TaskData` does not expose `updatedAt`. | Bulk changes and status actions can leave stale edit versions. Assign-to-me does not update the local assignees in `stateTask()`. | Use one board task serializer and reconciliation function across mutations; include version, assignees, workflow state, and ordering. Adapt Today data deliberately rather than mixing incompatible shapes. |
| P0 | `applyRealtimeSnapshot()` marks any dirty open task as conflicting, without comparing that task's server version. | Another person's unrelated task change produces a false warning and invites unnecessary overwrite. | Compare the edited task's baseline with its actual remote version. Preserve draft; warn only for changes to that task or deletion. |
| P0 | `applyRealtimeSnapshot()` unconditionally assigns server fields to `projectForm`. | A live update can erase unsaved project name/key/description edits. | Keep server state and settings draft separate; track dirtiness and project version; merge only untouched fields. |
| P1 | Board body uses both `x-init="init()"` and an `init()` method. | Initialization runs twice, registering duplicate socket callbacks, reconnect/keyboard/media listeners, and initialization work. | Remove the explicit duplicate call, make setup idempotent, and implement cleanup. Alpine [automatically calls init](https://alpinejs.dev/directives/init). |
| P1 | Comment/file uploads use XMLHttpRequest without `X-Socket-ID`, unlike `neovaFetch`. | The origin can receive its own events during a draft/upload. This interacts with false conflict detection and snapshot replacement. | Add socket header to XHR, return canonical state/version, and handle self events consistently. Adding the header alone is insufficient because comments also update task versions. |
| P1 | Snapshot failures only log to console. The board does not display the emitted connection-state events, and refreshes have no request timeout or retry/backoff. | People cannot distinguish saved work from disconnected collaboration or stale data. A hanging request can stall the refresher. | Add connection/subscription/snapshot health tracking, timeout, bounded backoff, and a retry action. Show saving, saved, failed, and updates unavailable separately. |
| P1 | Reconnection refresh exists, but no general focus/visibility reconciliation or fallback for persistent socket failure. | Missed changes can remain invisible until reload. | Refresh on return to a stale tab and successful subscription/reconnection; use rate-limited visible-tab polling only while degraded. Preserve drafts and scroll position. |

Focused executable checks exercised the actual inline `moveTask()` and `applyRealtimeSnapshot()` methods using controlled state and an HTTP stub. They confirmed retained old version/completion state after a successful move, a conflict on an unchanged edited task, and overwritten settings draft. These checks establish client behavior, not a production network diagnosis.

Production checks still required: verify the loaded Vite bundle's public Reverb host/scheme/port; HTTP 101 upgrade at `/app/...`; successful `/broadcasting/auth`; subscription acknowledgement; event receipt in a second client; snapshot response/application; proxy/service health; and stale-tab recovery. The existing deployment reference is `docs/reverb-production.md`. These events implement `ShouldBroadcastNow`, so a missing queue worker is not the direct explanation for this event class. Broadcast failures are caught/reported by middleware while the HTTP mutation may still succeed. Instrument these stages separately, without logging task content or credentials.

## Project management and deletion

Confirmed: the board entry is a 32px icon-only control (30×28px in mobile CSS); opening the drawer always selects Members. Deletion is inside Settings, below other settings. The Projects list provides board links and a creation form but no per-project management action. These facts support the discoverability problem reported by the user. Visible labels and recognizable options reduce memory demands, consistent with [NN/g's usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/).

Recommended flow:

1. Put a labeled `تنظیمات پروژه` (Project settings) button beside project identity, opening General settings directly. Keep a separate `اعضای پروژه` (Project members) entry when useful.
2. Add a clearly labeled project actions menu on each Projects row, alongside the board link. Offer Open board, Settings, Members, and Archive. Show permanent deletion in an explicitly named danger section or action with confirmation.
3. Organize settings as General, Members & access, Workflow, and Activity. Support direct URLs so an action from the list opens the intended section.
4. Add Archive/Restore for routine cleanup. This is new backend work: current deletion is permanent and the model deletes attachment files. Never offer Undo for hard deletion without implementing recovery and file retention.
5. Keep typed project-name confirmation for permanent deletion. Show the current project name, affected task/file counts, and consequence. Return to Projects with an explicit success message.
6. Bind displayed identity and deletion confirmation to current project state. The header and confirmation comparison currently embed server-rendered values, while AJAX settings save only updates `projectForm`; renaming can leave old labels and a confirmation name rejected by the server until reload.
7. Preserve owner/admin restrictions. For roles without management rights, explain the restriction in settings context and identify how to request help; do not grant broader permissions merely to simplify the UX.

## Broader board improvements

| Area | Current evidence / risk | Better behavior |
| --- | --- | --- |
| Feedback | Every board toast uses a green check, including errors; disappears after 2.5 seconds; lacks a live-region role. | Separate success/error/warning. Keep actionable errors visible with Retry; show validation next to fields. Announce status accessibly. |
| Settings safety | Drawer closes on backdrop/Escape with no dirty-state guard; live snapshots overwrite its draft. | Dirty-state tracking, explicit Save/Cancel, discard confirmation, and preservation during live updates. Members can remain immediate-save if clearly stated. |
| Keyboard | Task cards have `tabindex="0"` and click handlers but no Enter/Space activation. Project drawer lacks dialog semantics and focus trapping/return. | Use a proper task-opening control, keyboard activation, visible focus, accessible drawer tabs, initial focus, trapped focus, and focus return. Follow [WAI's modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). |
| Mobile movement | Cross-column mobile movement depends on dragging toward screen edges. | Make Move to column a prominent explicit task action, available by touch and keyboard. Keep drag as a convenience. Existing column selection in the editor can support this. |
| Filtered ordering | Sortable's visible `newDraggableIndex` is passed into the full task array. Hidden tasks make those indices differ. | Resolve drops relative to neighboring task IDs, or explicitly disable manual ordering while filtered. Verify both source and destination with hidden tasks. |
| Filter outcomes | Multiple filters can hide a newly created/moved task. | Explain “Created, hidden by your filters” with Show task/Clear filters. Distinguish an empty column from no matching tasks. Show visible/total counts. |
| Search | Board has local-search state/methods; shared shell exposes workspace search. The scope needs rendered validation. | Clearly label workspace search versus board filters/search. Support Persian ی/ي and ک/ك normalization and zero-width-space handling; preserve original display text. |
| Card density | Cards render title, description, assignees, tags, dates and indicators; many small text sizes occur in templates/CSS. | Prioritize title, responsible people, deadline/blocker. Make descriptions secondary and allow comfortable density. Validate actual legibility/contrast in rendered Persian UI. |
| Touch targets | Small project controls and other icon actions need device measurement. | Aim for 44px frequent mobile controls; verify the WCAG 2.2 minimum of 24×24 CSS pixels or applicable spacing exceptions. The current settings dimensions alone do not establish a WCAG failure. See [W3C target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html). |
| Task edit conflicts | Current resolution includes force overwrite; deleting a remotely deleted task's preserved draft closes it. | Keep/copy draft, compare changed fields, and require an explicit overwrite choice. Validate versions atomically server-side; timestamp comparison before a write is not a complete concurrency guarantee. |
| Empty states | Projects empty state is generic; creation requires a KEY pattern without a visible field label. | Show role-appropriate next steps; label Name/Project key; explain optional key/format; show creation errors next to inputs. |
| Workflow terminology | Board, Today, plans, done columns, blocking, and cycles introduce several state concepts. | Explain “assigned” versus “planned for today,” show named workflow statuses, and progressively expose cycle/WIP controls. Validate comprehension with new users. |
| Loading/activity | Activity load catches errors and replaces results with an empty array. | Distinguish loading, genuinely empty history, and failed history with retry. |

Retain useful existing work: quick task entry, filter chips, explicit task-save loading states, task draft protection, mobile column tabs, reduced-motion support, typed destructive confirmation, and drag rollback. Improve their consistency rather than rebuilding everything.

## Implementation order and release criteria

**Release 1 — Reliability:** one canonical mutation response model; reconciliation including affected siblings; correct task/project draft handling; single initialization; consistent socket headers; observable connection health and recovery. Regression coverage must include create→edit→edit, move→edit, sibling reorder→edit, bulk→edit, comment→edit, upload→edit, assign-to-me, done/reopen, unrelated remote updates during drafts, genuine same-task conflicts, and socket failure while HTTP remains healthy.

**Release 2 — Project actions and feedback:** labeled settings button; per-project actions; direct settings sections; reactive project identity/confirmation; persistent errors; accessible drawer. Archive/restore requires its own storage/recovery design and tests. Verify owner/admin/member/viewer behavior and prevent stale deleted-project navigation.

**Release 3 — Daily usability:** explicit movement actions; filtered-order correctness; empty/filter states; Persian search normalization; readable density and mobile targets; consistent keyboard behavior.

Suggested acceptance targets (proposed, not measured): 20 consecutive mixed board operations with no manual reload; zero false conflict banners from unrelated changes; two clients converge within two seconds on a healthy connection; unsaved drafts survive remote changes/disconnect/reconnect; correct ordering under filters; project settings found without hints within ten seconds; keyboard-only completion of core flows. Test healthy, slow, offline, expired-session, access-revoked, and deleted-project cases. Do not reload away a dirty draft on authentication/snapshot errors without a preservation/recovery path.

## User research needed to complete the audit

Run a small first round of moderated tests with Persian-speaking users, including new users and different roles, on desktop and mobile. About five participants per distinct user group is a useful initial qualitative round; iterate instead of treating five as proof of universal usability. See [NN/g's iterative testing guidance](https://www.nngroup.com/articles/why-you-only-need-to-test-with-5-users/).

Give outcome-based tasks without interface hints: create and edit a task twice; move and edit it; find an overdue task; rename a project; locate member management; remove a disposable project; recover after connection loss; handle another person's edit. Measure unassisted completion, time, wrong turns, reloads, errors, and understanding of save/delete consequences. Test deletion only with clearly designated disposable data in a test environment.

Use minimal product telemetry to compare before/after: mutation outcomes by action/status, conflict frequency, connection/subscription failures, snapshot freshness, retry frequency, and repeated reloads following writes. Avoid capturing descriptions, comments, personal details, or credentials. No user interviews or product analytics were available for this review, so visual and comprehension recommendations remain hypotheses until tested.
